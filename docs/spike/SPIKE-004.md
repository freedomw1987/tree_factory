# SPIKE-004：2 小時會議的成本形狀與上下文壓縮行為

- **對應 Module**：M02（記）／M03（問）
- **狀態**：✅ 完成（2026-10-08，trust mode 執行）
- **執行者**：trust mode 自動執行（`docs/trust-log.md`）
- **時限目標**：1 天內給結論 → 實際約 30 分鐘
- **結論一句話**：**成本不是風險，上下文窗口才是** —— 2 小時會議的模型費用粗估
  **US$0.07～0.50／場**（視模型與快取），但 Workers AI 的 `llama-3.3-70b-fp8-fast` **只有 24k 上下文**，
  而 2 小時逐字稿約 20k tokens → **壓縮與「用工具從資料庫檢索」是硬需求，不是優化**。

## 1. 為什麼要做這個 Spike

backlog 把「2 小時會議的 token 成本」與「Beta API 的長上下文行為」列為主要風險。
原本的擔心是「一直送整場逐字稿會不會很貴」，但遲遲沒有數字；
另一個沒被問出來的問題是：**上下文窗口夠不夠放一場 2 小時的會議**。

## 2. 實驗設計（零 API 成本）

| 手段 | 做法 |
| --- | --- |
| 結構量測 | 用 `faux` provider 餵 **120 回合**（每回合＝1 分鐘的會議逐字稿，約 235 字），量 entries 成長、是否觸發 compaction、`view.value` 有哪些欄位 |
| 用量會計 | 讀 Harness 內建的 `pi.usage` 文件（真實結構，數值由 faux 模擬） |
| 單價換算 | 用 Cloudflare 官方現行單價（2026-10-01 版定價頁）做算術，算式全部寫在下面 |

執行檔：`spike/spike-004/compaction.mjs`（`node compaction.mjs`）。

## 3. 實測結果

### 3.1 結構：一場 2 小時會議長什麼樣

```text
回合 | entries | 累積字元 | 回應狀態
   1 |       2 |      235 | done
  30 |      60 |     7050 | done
  60 |     120 |    14100 | done
  90 |     180 |    21150 | done
 120 |     240 |    28200 | done

entries 總數： 240
型別分佈： {"pi.user":120,"pi.assistant":120}
疑似 compaction 次數： 0
```

- **每分鐘 2 個 entry**（使用者送來的段落 + 助理的回應）→ 2 小時約 **240 entries**。
- 本次沒有觸發 compaction：逐字稿 28,200 字元 ≈ **約 11k～28k tokens**（中文字元約 1 token/字，
  保守取 28k），門檻設在 `reserveTokens=12000` 之下（faux 的 token 計數偏小），
  但**離 24k 窗口已經很近**——真實中文會議一定超過。

### 3.2 Harness 內建用量會計（重要）

```json
{"models":{"faux/faux-1":{
  "input":7914, "output":360, "cacheRead":470526, "cacheWrite":7914,
  "totalTokens":486714, "cost":{"input":0,"output":0,"cacheRead":0,"cacheWrite":0,"total":0}}}}
```

- **`pi.usage` 是真的存在的文件**，而且**逐模型記帳、還帶 cost 欄位**
  → 產品的「這場會議花了多少」看板不用自己造，直接讀這個文件。
- 結構上最值得注意的是 **`cacheRead` 47 萬 vs `input` 7,914**：
  Harness 每一回合都把「常駐上下文」重送一次，但**以快取讀取計價**，
  真正的新增輸入只有那一分鐘的段落。→ 成本模型必須把「快取折扣」算進去。
- 每回合平均：`cacheRead ≈ 3,921 tokens`、`input ≈ 66 tokens`、`output ≈ 3 tokens`
  （output 是 faux 的罐頭回應，不代表真實代理輸出，真實值待 SPIKE-004b）。

### 3.3 單價（Cloudflare 官方定價頁，2026-10-01 更新）

| 模型 | 輸入 | 輸出 | 上下文窗口 |
| --- | --- | --- | --- |
| `@cf/meta/llama-3.1-8b-instruct-fp8-fast` | $0.045 / M | $0.384 / M | 大 |
| `@cf/meta/llama-3.3-70b-instruct-fp8-fast` | **$0.293 / M** | **$2.25 / M** | **24,000 tokens** |

- Workers AI 以 **neurons** 計費：**$0.011 / 1,000 neurons**，免費額度 **10,000 neurons/日**。
- **前綴快取（prefix caching）預設開啟（部分模型）**，快取輸入另有折扣，
  且回應的 `usage` 會回報快取 token 數（正好對上 Harness 的 `cacheRead`）。

### 3.4 2 小時會議成本推估（算式攤開）

假設：2 小時、每分鐘 1 回合、共 120 回合；逐字稿 2 小時約 **20k tokens**（中文保守取 1 token/字）；
常駐上下文（含系統提示約 3k）平均約 13k tokens。

| 情境 | 輸入 tokens | 輸入費用 | 輸出 tokens（每回合 100） | 輸出費用 | 合計 |
| --- | --- | --- | --- | --- | --- |
| 70b-fast、**無快取**（最壞） | 120 × 13k = 1.56M | 1.56M × $0.293/M = **$0.457** | 12k | 12k × $2.25/M = **$0.027** | **≈ US$0.48** |
| 70b-fast、**快取生效**（實務） | 快取讀取約 1.5M（折扣約 1/4）+ 新增 20k | 約 **$0.11～0.13** | 12k | $0.027 | **≈ US$0.14** |
| 8b-fast（即時逐字稿階段） | 1.56M | 1.56M × $0.045/M = **$0.070** | 12k | 12k × $0.384/M = **$0.005** | **≈ US$0.075** |
| 會後生成筆記（單次，70b-fast） | 約 25k | $0.007 | 約 3k | $0.007 | **≈ US$0.014** |

**分階段策略的費用**＝即時逐字稿（8b）$0.075 ＋ 會後筆記（70b）$0.014 ≈ **US$0.09／場（2 小時）**。

> 免費額度換算：10,000 neurons/日 ≈ 約 **$0.11 的用量** → 一天大約只能跑 **1 場**會議（8b 方案）。
> 也就是說「免費版可行」但僅限輕度使用；要正式營運需 Workers Paid。

## 4. 驗收對照（backlog 風險項「2 小時會議成本」）

| 問題 | 結論 |
| --- | --- |
| 2 小時會議會不會貴到不能做 | ❌ 不會：**US$0.075～0.48／場**，分階段用模型約 **US$0.09** |
| 上下文窗口夠不夠 | ⚠️ **不夠**：70b-fast 只有 **24k**，2 小時逐字稿約 20k → 幾乎塞滿，加上系統提示與筆記必然溢出 |
| Harness 有沒有內建用量／成本追蹤 | ✅ 有：`pi.usage` 逐模型記帳（含 cost） |
| 有沒有壓縮機制 | ✅ 有：`CompactionPolicy { enabled, reserveTokens, keepRecentTokens, backgroundTokens }`，預設自動、可調 |

## 5. 對設計的影響（要回寫的文件）

1. **架構上「工具檢索優先」不只是省錢，是必須**：逐字稿的 source of truth 是產品自己的
   `transcript_segment` 表；代理要用 `ask()`／工具去查，**不要**期待「整場逐字稿都在上下文裡」。
   這正好符合既有設計（M02 獨佔寫入、M03 的 `ask()` 是唯一檢索點）→ **架構不變，但理由更硬**。
2. **分階段用模型**：即時逐字稿階段用 8b（便宜、快）＋會後筆記用 70b（品質）→ 成本降一個數量級。
3. **壓縮政策要顯式設定**：2 小時會議必然觸發壓縮；`reserveTokens` / `keepRecentTokens`
   要依 24k 窗口調（例如 reserve 6k、keepRecent 4k），並確保**壓縮不會吃掉尚未落表的段落**。
4. **成本看板直接讀 `pi.usage`**（per-model cost），不要自己重算 token。
5. **免費額度只夠一天約 1 場**（8b 方案）→ 定價／方案設計要以此為基礎。

## 7. 未驗證項（誠實列出）

1. **真實 token 數**：本次 `pi.usage` 的數值來自 faux provider（**結構真實、數值模擬**）；
   真實數字要用真 provider 跑一次（SPIKE-004b）。
2. **真實輸出長度**：即時階段的代理輸出（罐頭 3 tokens）不代表真實；若代理每回合回 300 tokens，
   輸出費用會從 $0.005 升到 $0.03～0.1（仍可接受，但要量）。
3. **延遲**：每回合送 13k tokens 的首字延遲未量（真實環境可能 0.5～2 秒）；不影響成本結論。
4. **快取折扣的實際比率**：依模型而異，本次以「約 1/4」試算，需以實測取代。
