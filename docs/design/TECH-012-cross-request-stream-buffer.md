# TECH-012 設計 — 逐字稿串流的跨請求等價：聚段緩衝改成「會議級」（D1~D10）

> 病灶（US-103 Gate 4 P0-1）：`#transcriptStreamRoute` 每個請求建一個 `TranscriptStream`，
> 聚段緩衝因此活在**請求**裡。請求一結束，緩衝裡那半句就跟著物件消失——**沒有錯誤、沒有回應欄位**，
> 帳本靜默少一句。同一個結構也讓「換一個 `meetingOffsetMs`」變成同一句話兩列。

## D1 緩衝是會議級，而且**落地在 DO SQLite**（`stream_buffer` 表，PK = `session_id`）

不只是在 DO 物件上放一個欄位（那仍是記憶體）：DO 隨時可能被平台回收，回收後「緩衝」消失＝
回到 P0-1。所以緩衝寫進同一顆 DO 的 SQLite（與 session／帳本同一份儲存），
用 `session_id`（＝`meetingId`）當主鍵，**一場會議一列**。

```sql
CREATE TABLE IF NOT EXISTS stream_buffer (
  session_id TEXT PRIMARY KEY,
  state TEXT NOT NULL,          -- JSON：{ meetingOffsetMs, words, pendingUtteranceEnd }
  updated_ms INTEGER NOT NULL
)
```

為什麼 `state` 存 JSON 而不是拆成一堆欄位：緩衝的形狀會跟著聚段器演進
（例如日後要記 `pauseThresholdMs`），拆欄位等於每次演進都要寫 migration。
代價是**讀取必須嚴格驗證**（見 D8）。

## D2 `meetingOffsetMs` 首值即權威（first-wins）

第一次以串流寫入的請求決定這場會議的 offset，**持久化**；之後每個請求都必須帶同一個值。

- **相同** → 照常寫入。
- **不同** → `409 OFFSET_MISMATCH`，附既有值 `meetingOffsetMs: <既有>`；**零寫入**、緩衝不動。
- 為什麼不是「以新的為準」：offset 是「音訊第一幀 ≠ 會議開始」的差額，同一場會議裡它是**常數**。
  改變它代表呼叫端前面算錯了——此時「重新對齊」會讓已經落地的句子變成孤兒，
  而「兩套時間軸並存」會讓同一句話的鍵不同 → 帳本兩列（票面已載明）。

## D3 `finalize: true` → 收尾落地 ＋ 清空字、**但保留 `meetingOffsetMs` 的釘樁**（冪等）

`flush()` 的冪等性（第二次回 `null`）讓重送 `finalize` 不會多一句；緩衝的字清空，
下一次寫入自然從新段落開始。

**修訂（真 workerd 冒煙抓到，見 §7）**：第一版是**刪掉整列**，結果 `meetingOffsetMs` 的釘樁
一起被刪掉——重新連線的裝置端帶一個重算過的 offset 回來，D2 的 first-wins 保護直接失效，
已落地的句子在 0~1 分鐘、新的句子整批跳到 offset 之後。現在收尾寫入的是
**「只有釘樁」的列**（`{ meetingOffsetMs, words: [], pendingUtteranceEnd: false }`），
`finalize()` 也一併消費延後的 endpointing 訊號（否則它會跟著快照活到下一條串流，
讓下一句開頭白白多切一刀）。會議真正結束時走的是 D4 的 `drop()`（整列刪掉）——
那時會議已經不會再有請求，釘樁沒有意義。

## D4 會議邊界：只認**當前** session

讀到的列若 `session_id !== 目前 meetingId` → 視為不存在（不回傳舊字）。
另外兩條路徑也要清：

- 請求被 `#transcriptWriteRejection` 擋下（會議已結束／達 2 小時上限）→ 刪掉該場緩衝，
  並在 409 body 附 `droppedBufferedWords: <n>`：**明講**「未完成的那段沒有落地」，
  不假裝它不存在（誠實原則；丟的是「還沒講完的半句」，不是已完成的句子）。
- 新會議（新 `meetingId`）不會读到舊列，所以不會繼承。

## D5 緩衝有界 → **強制收段**（不是丟字）：**字數 ＋ 字元**兩個上限，逐字檢查

正常情況下緩衝只裝「還沒講完的那半句」（數十字）。若一路沒有停頓／換人／`UtteranceEnd`，
它理論上可以無限長。做法是在餵進聚段器之前**逐字**檢查：收下這一顆字會不會超過上限？
會，就先把緩衝中那一段**收段落地**（`forcedFlushes` 計數加到回應），再收下這顆字。

上限有兩條，**缺一不可**：

| 上限 | 預設 | 擋什麼 |
| --- | --- | --- |
| 字數 `maxBufferWords` | `MAX_BUFFER_WORDS = 2000` | 那一列快照（SQLite）無限長大 |
| **字元 `maxTextChars`** | 帳本的 `MAX_TEXT_CHARS = 2000` | 收下來的段落**落不了地**（帳本會 400） |

**第二條是 Gate 4 第二輪 oracle 抓到的 P1**（第一版只有字數上限）。症狀在真 workerd 上：

- 一次請求送 2001 顆字（真人要連講 13 分鐘不換氣才自然產生，但呼叫端也可以一次補送一整段）。
- 字數上限 2000 **不會**觸發：舊守衛是「逐批」檢查（`緩衝 + 本批 > 上限`），一批本身就超過時
  它只能放行；而且 2001 > 2000 也只在**收下之後**才成立。
- 聚段器於是產出一顆 **12005 字元**的段落 → 帳本 `MAX_TEXT_CHARS` 拒收 → **每次請求都 400**，
  `forcedFlushes` 永遠 0；那 2001 顆字只在會議結束時以 `droppedBufferedWords` 現形。
  「一字不丟」在這一格是假的——守衛製造了它要防的那個結果。

修法兩個動作（都在 `worker/src/transcript-stream.ts`）：

1. **逐字餵**（`#feedLanding()`）：每收一顆字前問一次 `#overflows()`。逐字與逐批在聚段語意上
   等價（聚段器本來就是逐字判斷切點），但逐字之後**任何請求都不可能讓緩衝超出上限**，
   強制收段的段落也一定落得了地。
2. **字元預算**（`#overflows()` 第二條）：`join 長度 + 1 + 這顆字的長度 > maxTextChars` 就切。
   用 join 長度是刻意的——它是 `buildSegment()` 真正產出的 `text.length` 的**上界**
   （`trim()` 只會更短），所以「join 長度 ≤ 上限」保證「text ≤ 上限」→ 落地一定成功。
   字數的長度**只算 `punctuated_word`**（落地用的就是它；用 `word` 會低估預算）。

兩條判準都是「**超過**才切」：恰好等於上限時不切（切了會多出沒有人要的碎句）。

- 為什麼不是「拒收請求」：拒收會讓呼叫端卡在一個「不管送什麼都被擋」的狀態（還要先知道上限）。
- 為什麼不是「丟掉字」：那一句會**太長**，但逐字稿一字不丟是本產品的地基。
- 字數上限選 2000：約連講 13 分鐘，是一條**防禦線**（真跡 38 則訊息最多的一段是 6 個段落）。
  字元上限不是防禦線，它是「帳本收得下」的精確條件；實際上**通常由它先觸發**（見 §6 第 9 點）。

## D6 顯示用的 interim 緩衝**不**持久化（明講，不是忘了）

落地的緩衝（`#segmenter`）與顯示的緩衝（`#display`）在設計上是兩套。只有前者持久化：

- 落地緩衝的**最後一段**（final 的字）會當成顯示緩衝的種子（`resume`）：那半句是已知的，
  不餵給顯示層等於每次換請求畫面就跳一下。**interim 的內容不落地、也不進快照**——
  它下一則累積重述會自己補回來，這是「自癒」，不是資料遺失。
- 持久化短命資料＝每個請求多一次寫入，而正確性收益是 0（落地不依賴它）。

文件與設計都要寫清楚：**`pending` 在請求邊界可能瞬時歸零**，US-104 的顯示層不得把它當成
「這句被刪掉」（US-104 的 `applyInterim` 是覆蓋式寫入，天然相容）。

## D7 快照只在「整批成功」之後才寫

順序：`ingest()` → `finalize()`（若有）→ **寫快照**。

- 中途拋錯（例如某一句落在未來時間窗 → 400）時**不寫快照**：緩衝留在請求進來前的狀態，
  呼叫端可以原封不動重送同一批（冪等鍵保證重送安全）。
- 這個順序讓「帳本已落地」與「緩衝已前進」不會出現「緩衝前進了但字沒落地」的方向
  （那個方向才是丟字）。

## D8 壞掉的持久狀態 → 大聲失敗（500 `STREAM_BUFFER_CORRUPT`）

驗證 `state`：必須是 JSON 物件、`meetingOffsetMs` 非負整數、`words` 是陣列且每個元素
`{ word, speaker, start, end }` 形狀正確（`punctuated_word` 選填）、`pendingUtteranceEnd` 布林。

驗不過 → `StreamBufferCorruptError`（`recoverable: false`）。**不得**當成「沒有緩衝」繼續：
那等於把 P0-1 的靜默少字換一個觸發條件。

## D9 介面（加法）

`POST /transcript/stream` 回應新增四個欄位，既有欄位語意不變：

| 欄位 | 意義 |
| --- | --- |
| `meetingOffsetMs` | 這場會議的權威 offset（＝首值，回聲給呼叫端對齊） |
| `bufferedWords` | 目前緩衝裡的字數（**看得見**「有一句還沒完成」） |
| `forcedFlushes` | 這次請求因為 D5 強制收段幾次（0 = 沒發生） |
| `replayedWords` | 這次被判定成「早就落地的重播字」而**沒餵進聚段器**的字數（見 D10 修訂） |

`replayedWords` 與 `duplicates` 是**兩種單位**，刻意不合併：`duplicates` 是**段落級**
（帳本的冪等鍵命中，回的是整列），`replayedWords` 是**字級**（重播的整批事件裡、時間軸
早已被帳本蓋到的那幾顆字）。這些字是被**丟掉**的——丟得對（帳本已蓋到，丟了不掉字），
但裝置端必須看得出來「這一批有東西被忽略」，不能再靠會議結束的 `droppedBufferedWords` 才知道。

`pending` 改由持久緩衝還原（同源）。另外 409 的兩種 body 各多一個欄位：
`OFFSET_MISMATCH` 帶 `meetingOffsetMs`；會議已結束／達上限帶 `droppedBufferedWords`。

## D10 重播去重：接續的字若**身分相同**＝重播，不得再餵一次

裝置端是 at-least-once（回應在路上掉了就重送同一批）。已落地的段落有冪等鍵擋著，
但**還在緩衝裡的那半句**沒有鍵可用——照單全收會變成「甲 甲」疊字，之後落地時內容與
已落地的列不同 → 變成 `conflict`（那句話就沒了）。

判準是「**身分完全相同**」：講者＋起訖秒＋字面（`wordIdentity`）。**在 final 序列裡**
同一顆字不可能用同一組時間戳出現兩次（`spike-001` 真跡裡同身分的重複**只出現在 interim**——
interim 會累積重述、重用時間戳，而本表只由 final 字建、也只對 final 判去重，所以碰不到它們）。
配掉的一定是重播。實作上 `TranscriptStream` 用從 `resume` 建的去重表（`#takeFresh()`）逐顆扣掉；
整批都是重播時**什麼都不做**（連延後的 `UtteranceEnd` 收段都不做，否則重播一次就把緩衝提前清空、
狀態就不冪等了）。

已知限制（措辭要精準，這一條曾被審查抓到寫得太寬）：

- 只有**改掉 `word` 或時間戳**的重播會走衝突路徑——**大聲**（`conflicts` 非 0），不是靜默。
- 只改 `punctuated_word` 的重播：身分不含標點，會被**當成同一顆字去重**（靜默、不疊字，
  但也就不會把新的標點寫進去）。
- 去重只認「原樣重送」；重送時**順序**可以不同（身分比對，不是位置比對）。

### D10（修訂二）— 只認「緩衝」不夠：**已落地**的字要看帳本

第二輪 Gate 4 的 oracle 抓到：裝置端重送的是**整批事件**，裡面同時有「還在緩衝裡的字」
（上面那張身分表認得）與「**已經落地**那半句之後的字」（不在那張表裡）。後者照單全收就會
被接在「時間較晚的緩衝字」後面，緩衝時間軸反向 → 下一次落地被 `validateSegment` 擋成
400；而壞掉的順序**已經寫回 SQLite**（每個請求都重新 `buffers.read()`）→ **之後每個請求都 400**，
字只在會議結束以 `droppedBufferedWords` 出現。實測重現見交付文 §7 第三輪。

判準改成「**已經落地、而且餵了會打亂緩衝順序**」才丟，兩個條件都成立才成立（缺一不可）：

1. **會打亂順序**：這顆字的**終點** ≤ 緩衝現有內容的終點（毫秒）。
   緩衝空、或字本來就接在緩衝後面 → 條件不成立 → 照舊餵進聚段器。
   用**終點**而不是起點：起點剛好等於已落地那列終點的新字（合法的下一句）終點更大，
   不會被誤殺——它會被條件 2 擋下來。
2. **帳本已經蓋到它的終點**：`sink.previousEndMs(字終點) >= 字終點`
   （＝帳本有一列的 `start_ms` 在這顆字之前，且那列的 `end_ms` 已經追平／超過它）。
   這是「**丟了不掉字**」的保證：條件 2 不成立的字（例如 US-102 回補送來的舊音訊字）
   **一律不進判準**，即使它排在緩衝前面——那些字還沒落地，丟了就是真的掉字。

被丟掉的字要**報出來**（`replayedWords`，D9 的第四個欄位）：丟得對，但不能靜默。
「整批都是重播時什麼都不做」這條**不變**：被丟光的批次 `fresh` 是空的，
連延後的 `UtteranceEnd` 也不消費（狀態照樣冪等）。緩衝空時的重播也**不變**：
一個字都不丟，照舊交給帳本的冪等鍵判 `duplicate`（US-103 AC-4/AC-1
「整批重播 → 全部 duplicate」的既有承諾，`transcript-ledger-routes.test.ts` 釘著）。

修訂二的已知取捨（刻意的，不是承諾）：

- **沒被帳本蓋到、又排在緩衝前面的字**仍照原樣餵進聚段器（來源時序外送）。那條路的
  時間軸本來就可能反向——本票不處理，記在交付文的未開票遺留。
- 帳本只有**段級**的時間覆蓋、沒有逐字身分，所以條件 2 是**以時間軸判定**的：
  兩位講者的字在同一段時間內交錯、且較晚的那批已先落地時，較早的那批會被判成重播丟掉
  （`replayedWords` 看得見，不是靜默——**但可見範圍只到 HTTP 回應層**，UI 沒有消費者，見 §6 第 13 條）。

**編號註記**：本檔的 D 編號是**本檔自己的序**（D1~D10）。`transcript-stream.ts` 檔頭那份
「模組決策清單」是 US-103 的序，那份的 `D10` 指 `finalize()` 收尾（本票沿用、沒有改編號）；
因此該檔註解提到重播去重時一律寫成「**TECH-012 D10**」，程式裡同時存在兩個 D10 是刻意的、
不是筆誤。

## §6 已知限制（明講，不假裝已驗）

1. **顯示緩衝不持久**（D6）：`pending` 在請求邊界可能瞬時為 `null`。
2. 本票保證「**怎麼切都等價**」，但**不**保證「呼叫端會怎麼切」——切法仍由呼叫端決定
   （US-103 的 `finalize` 契約仍然有效，只是不再是正確性的必要條件）。
3. `MAX_BUFFER_WORDS` 的 2000 是**防禦線**，沒有真會議壓測過；超過時的行為有測試釘住。
4. 真 workerd 冒煙涵蓋拆請求／offset／finalize／DO 重建；**併發**兩個串流請求交錯仍不在本票範圍
   （單一 DO 單執行緒，但 `await request.json()` 期間的交錯屬 TECH-013 的計數議題，已在那裡處理）。
5. D10 的去重假設「來源是 at-least-once 的**原樣重送**」：改 `word` 或時間戳的重播會走衝突路徑
   （大聲，不靜默）；只改 `punctuated_word` 的會被當成同一顆字（見 D10 段的措辭）。
6. 顯示層的 `pending` 仍是「顯示緩衝」的視角：`UtteranceEnd` 一到就被 flush，那一瞬間 `pending` 是 `null`
   （既有 US-103／US-104 行為，本票沒有改動它）。
7. **D8 的形狀驗證沒有擋負的時間戳**（只驗有限數）：負值會在**落地時**被
   `validateSegment` 擋成 400 `TRANSCRIPT_INVALID`（大聲、不是靜默、也不是「合法 JSON 直接 500」型缺陷），
   所以**刻意不修**——本票的 `STREAM_BUFFER_CORRUPT` 只負責「這份 JSON 根本不是緩衝」。
   來源：Gate 4 第一輪 reviewer 的 P3-2。
8. **D5 的兩個上限都是「超過才切」**（恰好等於上限不切）。逐字檢查之後不存在「一批就衝破上限」
   的情形（第一輪 reviewer 的 P3-3 因此不再成立）。**單一 token 本身**就超過帳本上限的字，
   在**收進來之前**就被擋（見下面第 10 條）：不能讓它進緩衝。
9. **字數上限在預設組態下「不會」先觸發**（可設定的第二道保險）：一顆字至少 1 個字元，
   而 `joinedTextLength` 的 `(n-1)` 讓 ~1001 顆字就必然超過 2000 字元，所以預設值下
   `buffered.length >= maxBufferWords` 這條**到不了**（原文「幾乎不會先觸發」說得太鬆）。
   它只在呼叫端把 `maxBufferWords` 調小時才會先到頂——測試就是注入 3／2 來驗它，兩條都測到。
   來源：Gate 4 第二輪 reviewer 的 P2-1（措辭修正，不動程式）。
10. **單一 token 超過帳本上限 → 收進來之前就 400**（修訂二，Gate 4 第二輪 oracle 的 P2）。
   這種 token 實務上不存在（一顆字不會有 2000 字元），但放行之後它會**先被收下**，
   之後同一場會議的**每一次請求都 400**（連正常字也落不了地），直到會議結束以
   `droppedBufferedWords` 收場——整個緩衝變毒藥。現在在 `#feedLanding` 的字迴圈開頭就
   丟 `TranscriptInvalidError`（路由轉 400，訊息指名長度與上限），緩衝維持乾淨、
   後續正常字照常可用。測試釘住（`M01-D5：單一 token 超過帳本上限…`）。
11. **形狀合法、但緩衝總長超過上限的快照**：`resume` 之後的第一個請求會 400（`#overflows` 擋掉）。
   本碼自己寫出的快照不可能超上限（每次寫入前都過 `#overflows`），只有外部破壞／舊格式資料才踩得到。
   **不修、未開票**（Gate 4 第二輪 reviewer 的 P2-2，交付文 §6 第 11 條）。
12. **D10 修訂二的判準是「時間軸覆蓋」，不是逐字身分**：兩位講者的字在同一段時間交錯、
   而較晚的那批**已先落地**時，較早的那批會被判成重播而丟掉——`replayedWords` 看得見（不是靜默；
   UI 沒有消費這個欄位，見第 13 條），但那一批字就沒了。這個形狀沒有真跡可對照
   （`spike-001` 是單人獨白混 interim），只有單元層的合成資料走過（交付文 §6 第 3 條、AC-9）。
13. **被丟掉的重播字，UI 看不到**（Gate 4 第三輪 oracle 的 P2-1，**report-only、未開票**）：
   唯一的痕跡是那一次請求的回應欄位（`app/ui` 零消費者，`grep -rn replayedWords app/ui/src` = 0）。
   要不要接到 UI 告警／會議結束摘要＝新票（交付文 §6 第 13 條）。
