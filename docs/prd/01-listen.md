## 1. 這個 Module 存在的理由

把**聲音**變成**有名字的逐字稿**。

它是整個產品最靠近硬體與網路的一段：麥克風、iOS 生命週期、行動網路的不穩定，都在這裡發生。
也是唯一能證明「手機放在會議桌上真的可以拿來記錄」的一段。

**一句話成功標準**：使用者在會議室按下開始，把講話變成螢幕上看得見、有名字、斷線也不掉的逐字稿。

## 4. 依賴關係

```text
TECH-001（環境前置）
   └─▶ SPIKE-002（iOS 收音可行性）
          └─▶ M01-US-101（開始/結束錄音）
                 └─▶ M01-US-102（分段緩存與回補）

TECH-001
   └─▶ SPIKE-001（diarize 可行性）★ 全案最大未知數
          └─▶ M01-US-103（多人即時轉譯）
                 ├─▶ M01-US-104（即時顯示）
                 └─▶ M01-US-105（speaker 命名）

M01-US-101 + M01-US-103 + M02-US-201 ─▶ INT-M01-M02-01（端到端）
```

**向上依賴（本 Module 需要的、由 M02 提供）**：M02-US-201 提供 `ack` 語意，M01-US-102 的冪等鍵設計需與其一致。

**向下依賴（別的 Module 需要本 Module）**：M02-US-203 需要 M01-US-105 的命名結果才能顯示正確人名。

⚠️ **依賴風險**：M01-US-103 的整條路都掛在 SPIKE-001 上。若 `diarize` 串流不可行，M01-US-103/104/105 的設計需重做
（可能改為批次 diarize + 時間戳對齊），估點也會變。SPIKE-001 必須最先跑。

## 6. Non-goals（本 Module 明確不做）

| 不做 | 理由 |
| --- | --- |
| 背景 / 鎖屏持續錄音 | 需 Swift 原生層（backlog §5）|
| 邊錄邊上傳的即時串流最佳化（WebRTC / QUIC）| v1 先求正確，不求延遲極小 |
| 本地端離線 STT | 行動裝置算力不足，且與「音訊不離開 Cloudflare」的決策衝突 |
| 自動偵測會議開始 / 結束 | 誤判成本高，v1 一律手動 |
