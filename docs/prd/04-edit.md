## 1. 這個 Module 存在的理由

讓 AI 的產出**不再是不可質疑的黑盒**：錯字可以改、摘要可以改、概念可以改名與合併。

它對應的是產品哲學 P8：**AI 的產物都可修正**，但分兩層處理——

- **事實層**（逐字稿）：有人真的說過這句話 → 改動必須留痕（`edited_at`，決策 D8）
- **推論層**（摘要 / 待辦 / 概念）：AI 的歸納，本來就不是事實 → 直接改，不留旗標

**這條分層線就是本 Module 的設計核心**。做錯方向會出現兩種失敗：對推論層要求旗標 → 使用者覺得囉嗦；
對事實層不留痕 → 使用者以為那是機器原始輸出（D7 的不可逆代價，必須靠旗標緩解）。

**一句話成功標準**：使用者改了一個 STT 錯字 → 逐字稿畫面乾淨得像沒改過；
但當 AI 引用那句話時，它自己會說「此句有人工修正」。

## 4. 依賴關係

```text
階段 A（M01 / M02 的逐字稿與三層記錄）
   ├─▶ M04-US-401（逐字稿可編輯）◀── 依賴 M02 的 edit_segment（寫入權在 M02）
   │      └─▶ M04-US-402（編輯旗標）◀── 依賴 M03 的來源契約（標示在來源處）
   │             └─▶ ★ M04-US-402 與 M03-US-302 有雙向約束（同一根旗標的寫與讀）
   └─▶ M04-US-403（推論層編輯）◀── 依賴 M02-US-202 的 finalize_notes / upsert_action
          └─▶ SPIKE-006（概念提取粒度）
                 ├─▶ M04-US-404（概念提取與概念卡）
                 │      └─▶ M04-US-405（瀏覽與合併）
                 └─▶ M04-US-406（標籤）◀── 也可獨立於概念層先行（標籤可只對會議）
```

**向上依賴（本 Module 需要的）**：M02 的編輯 API（`edit_segment` / `edit_note` / `edit_action`）與讀取 API；
M03 的來源結構（`meeting_id` / `source_seq` / `edited_at`）。**M04 不直接寫 M02 的表**（`system-design.md` §3）。

**向下依賴（別的 Module 需要本 Module）**：M03-US-302 的「此句有人工修正」需要 M04-US-402 寫的旗標；
M03-US-307 的標籤篩選擴充（階段 C 後）需要 M04-US-406。

⚠️ **依賴風險（本專案最大的一條）**：`M04-US-402 ↔ M03-US-302` 是**跨 Module 的雙向約束**——
旗標由 M04 寫、由 M03 讀。若拆票時把兩者分給不同人且不同時完成，會出現「改了但沒人標」的靜默缺陷。
**緩解**：`system-design.md` §5.4 規則 4 把讀取責任釘在引擎端，且 §3 把寫入權釘在 M02 端，
兩端都不在自己手上「各寫一份」。

- **FR-406 的畫面在 M03**（對話來源卡）：旗標由本 Module 寫、由 M03 顯示，

- **`05-concept.html` 屬本 Module 的第二份原型**：概念層畫面數多（列表 / 卡 / 合併 / 搜尋 / 標籤），

## 6. Non-goals（本 Module 明確不做）

| 不做 | 理由 |
| --- | --- |
| 記錄版本歷史 / 還原舊版 | 決策 D7：使用者要的是「改掉就好」；舊版對修錯字無幫助。**代價已知**：改回原樣仍標示（FR-407）|
| 多人協作編輯 / 衝突解決 | 單人自用（決策 R5），無並發編輯情境 |
| 手動新增概念 | v1 只讓 AI 抽取（`DESIGN.md` §4.5 決定 4）；手動建會產生「使用者建了但 AI 認不出」的落差 |
| 編輯 speaker 名稱或時間戳 | 改名走 M01-US-105；時間戳是 STT 的事實，不可改（FR-402）|
| 概念層的主動推播 / 自動關聯圖 | v1 只做列表、卡、合併、搜尋、標籤；視覺化關聯圖列 v2 |
| 標籤的自動套用（未經確認）| M04-US-406 AC-3：建議標籤需使用者確認才生效 |
| 跨裝置同步編輯結果 | v1 單機；DO 為唯一來源，但無多裝置衝突處理 |
