## 1. 這個 Module 存在的理由

把「一疊會議記錄」變成**可問的記憶**——而且**問不到就說問不到**。

它是階段 B 的全部內容（35 SP）：會議記錄從「事後翻閱」升級成「隨時可問」。
同時它也是本產品最容易被做壞的地方：同類產品最大的失敗不是答得不好，是**答得很順但沒有依據**。
因此本 Module 的第一條功能不是「回答」，是「**誠實**」（P7、M03-US-305 的 20 題負向探針）。

**一句話成功標準**：使用者問「上次那筆預算是誰負責？」→ 拿到答案 + 一句可點的來源；
問「明天天氣如何」→ 直接被告知超出範圍，**而不是拿到一段聽起來很合理的廢話**。

## 4. 依賴關係

```text
M01 / M02 的逐字稿與三層記錄（階段 A 完成）
   └─▶ SPIKE-005（跨會議檢索方式）★ M03 的架構級未知數
          ├─▶ M03-US-301（對話框首頁）
          │      └─▶ M03-US-302（附來源）
          │             └─▶ M03-US-303（跨會議彙整）◀── 需要多場記錄存在
          ├─▶ M03-US-305（查無不編造）★ 負向題組需人工建立（真實工作量）
          │      └─▶ M03-US-306（中斷與重試）
          └─▶ M03-US-307（範圍鎖定）◀── 由 M02 的「問這場」入口進入
                 └─▶ INT-M02-M03-01（M02-US-205 為呼叫端）
M03-US-304（對話歷史）依賴 conversation / message 表（§6），與檢索方式無關，可並行
```

**向上依賴（本 Module 需要的）**：M02 的逐字稿讀取 API（`transcript_segment` 的 `seq` / `text` / `speaker` / 時間戳）
，以及 M02 的 `edited_at`（FR-317 的標示依據）。**M03 不直接讀 M02 的表**，只透過讀取 API（`system-design.md` §3）。

**向下依賴（別的 Module 需要本 Module）**：M02-US-205（單場語音追問）與 INT-M02-M03-01；
M04-US-404/405（概念卡的來源句格式與來源回溯共用同一套來源結構）。

⚠️ **依賴風險**：SPIKE-005 未跑前，M03 的**檢索方式**未定（全文 / 向量 / 直接餵 LLM）。
這會影響成本與「來源可回溯」的實作難度，但**不影響任何使用者可見的 AC**（AC 只約束行為與誠實度）。

- **`INT-M02-M03-01` 登記於本檔 §5.1**（不在 M02 的 PRD 重複列為 FR）。

  v1 只做「全部 / 本場」兩種，標籤篩選為後續擴充。

## 6. Non-goals（本 Module 明確不做）

| 不做 | 理由 |
| --- | --- |
| 修改任何會議資料 | 決策 D6：對話框 v1 **只讀**（可問、可看、可回溯，不可改）|
| 對外發送（Email / Slack / 分享回答）| 外部授權與隱私風險，v1 不做（backlog §5）|
| 主動推播 / 定時摘要 | 使用者沒問就出聲違反 P1 的精神（是使用者叫它，還是它自己冒出來）|
| 對話歷史的主題分組與自動命名 | 決策 D12：階段 B 實作後再觀察，v1 先線性列表 + 時間（M03-US-304）|
| 引用「會議以外的知識」（網路 / 常識）| 違反 P7「沒有來源就不說」；超出範圍一律明說（FR-311）|
| 多輪追問的指代消解做到完美 | v1 靠「同一對話串的上下文」處理，不追求跨對話串的指代；不足之處記為已知限制 |
| 語音輸入 | 決策 D11（`DESIGN.md` §7），Step 4.5 前拍板；若做，另開票 |
