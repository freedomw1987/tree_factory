### 0.2 SWOT（戰略決策：v1 定位 = 會議記錄，而非一對一語音對話）

> 觸發條件：戰略影響 + 高成本（本決策定調整個 v1 的資料模型與 agent 設計，且推翻初始「AI 會回話」的直覺）

| 象限 | 內容 |
| --- | --- |
| **S 優勢** | 語音轉譯與 diarization 在 Cloudflare 有現成模型，不必自建 STT |
| **W 劣勢** | 會議記錄是紅海；Pi Durable 為 Beta，API 會變動 |
| **O 機會** | 逐字稿＋待辦的耐久性（斷網/閃退不遺失）是現有 app 少有的差異點 |
| **T 威脅** | 2 小時會議的 token 成本與 compaction 品質若不穩，整個價值主張會崩（上限已定為 2 小時，故成本以 2 小時為基準估）|

斷線/閃退可續且不重複計帳。

### 0.3 v1 三階段交付（決策 D9）

> 觸發條件：戰略影響 + 高成本 + 不可逆（定義整個 v1 的交付順序與首頁 IA）

用戶於 2026-10-07 新增產品方向（R6）：Agent 第一版的入口是**對話框**（從過去的會議記錄問答）、
會議記錄要像 **wiki**（概念提取）、且**會議記錄可編輯**。經提問收斂為
「**v1 全包但分三階段，先做資料再對話**」。

| 階段 | 內容 | 使用者入口 | 階段驗收（可獨立交付）|
| --- | --- | --- | --- |
| **A 資料基礎** | 錄音 → 逐字稿 → 三層記錄 → 匯出 | 會議分頁 | 能錄完一場 2 小時會議並匯出記錄（**無**任何問答能力）|
| **B 對話** | 對話框為首頁、跨會議檢索問答、對話歷史、單場追問 | **對話框（首頁）** | 能問「上週預算會議結論是什麼」並點開來源句 |
| **C 知識層** | 記錄可編輯、概念提取、交叉引用、標籤 | 對話框 + 概念分頁 | 記錄可修正（含錯字）、概念可瀏覽與回溯 |

各階段涵蓋的項目與 SP 見 §2.1。

**首頁 IA 反轉（決策 D9 的一部分）**：階段 B 起首頁 = 對話框，會議列表降級為「會議」分頁。
階段 A 期間首頁仍為會議列表（還沒有可問的東西）。
**此反轉必須先在 `DESIGN.md` 畫面樹記錄**，避免階段 A 的實作者把首頁寫死、B 時要大改。

**為什麼不「全部一起做」**：對話沒有會議記錄是空殼（檢索無資料）；且階段 A 的 107 SP 已規劃完成，
先讓它跑起來可驗證核心風險（SPIKE-001 diarization）而不必等 M03/M04 設計完。

## 1. Module 定義

v2.0 現況：**4 個 Module**（M01 聽 / M02 記 / M03 問 / M04 編）＝「資料 → 對話 → 知識層」三階段。

歷史：v1.0 依**技術層**切成 4 個（app-shell / voice-pipeline / agent-core / notes）→ v1.1 依**功能內聚**
重切為 2 個（聽 / 記）→ v2.0 因新需求（對話框 / wiki 概念 / 可編輯記錄）擴張為 4 個。
兩次重切的理由分別見下方兩節。

| Module | 名稱 | 一句話職責 | 涵蓋 US | DoD 深度 |
| --- | --- | --- | --- | --- |
| **M01** | 聽 | 把聲音變成**有名字的逐字稿** | M01-US-101 ~ 105（5 US）| DoD-Full |
| **M02** | 記 | 把逐字稿變成**耐久可查的記錄** | M02-US-201 ~ 205（5 US）| DoD-Full |
| **M03** | 問 | 把記錄變成**可問答的知識**（附來源）| M03-US-301 ~ 308（8 US）| DoD-Full |
| **M04** | 編 | 讓知識**可修正、可瀏覽**（事實層 / 推論層 / 概念層）| M04-US-401 ~ 406（6 US）| DoD-Full |

**M01 / M02 的介面（唯一通道）**：append-only 逐字稿事件流

```text
{ seq, idempotency_key, speaker_id, start_ms, end_ms, text }
```

- `seq`：會議內單調遞增序號（M01 產生）
- `idempotency_key`：由音檔分段序號導出（M01 產生，M02 用它去重）
- M02 可用**假事件**獨立測試，不需真的收音 → 符合「可獨立測試」

**M02 ↔ M03 的介面**：單場追問與跨場對話**共用同一套檢索與回答引擎**（見 `INT-M02-M03-01`）。
沿用已批准的 D1 模式（**引擎歸一個 Module、UI 入口在另一個**）：

| 角色 | 歸屬 |
| --- | --- |
| 問答引擎（檢索 → 回答 → 附來源）| **M03** 擁有 |
| 單場追問入口（`scope = meeting_id`，含 TTS）| M02-US-205 呼叫 |
| 跨場對話（`scope = all`）| M03-US-301 / 303 / 307 呼叫 |
| 發言者命名**資料層**（先例）| M01-US-105 擁有，UI 在 M02 |

**Module 欄對 Spike 的語意**：Spike 的 Module 欄代表「**本 Spike 的結論會改變哪個 Module 的設計**」，
不是「本 Spike 屬於該 Module 的交付物」。TECH 項（基礎建設 / skill 修補）不綁 Module，故填 `—`。

### 為什麼 M03 / M04 獨立成 Module（v1.1 → v2.0）

| 面向 | 塞進 M02 | 獨立成 M03 / M04（v2.0）|
| --- | --- | --- |
| 功能內聚 | M02 同時負責「產生記錄」「檢索問答」「概念提取」「編輯」| 產生 / 問答 / 編輯各有獨立失敗模式與獨立知識 |
| 可獨立交付 | 無法階段交付（A/B/C 綁死）| 對應 §0.3 的三階段，各階段可單獨驗收 |
| 可獨立測試 | 檢索邏輯無法獨立於記錄產生測試 | M03 可用假逐字稿事件獨立測試（同 M02 現行做法）|
| 粒度 | M02 膨脹到 11 US 且混三種性質 | 5 / 7 / 6 US，皆落在 3-15 區間 |

### 為什麼重切（v1.0 → v1.1）

| 面向 | v1.0（4 Module）| v1.1（2 Module）|
| --- | --- | --- |
| 切割依據 | **技術層**（外殼 / STT / agent / 記錄）| **功能內聚**（聽 / 記）|
| US 分布 | 2 / 2 / 2 / 3 | 5 / 5 |
| 合規性 | ❌ M01-M03 皆 2 US，違反「3-15 US / Module」| ✅ 皆 5 US |
| 探針邊界 | 綁在實作層，換 STT 供應商要動 Module 邊界 | 綁在功能層，換 STT 只動 M01 內部 |
| PRD 份量 | 3 份薄 PRD（2 US 沒什麼好寫）| 2 份有內容的 PRD |

**根因**：v1.0 是照「技術分層」切，會被 dav-designer 的「功能內聚」原則反例命中的正是這一類。
重切時機選在**零程式碼階段**，成本僅文件；若等寫了 code 才重切，需同步改檔名 / import / 探針 / CI。

## 5. Non-goals（v1 明確不做）

| 不做 | 理由 |
| --- | --- |
| Android | 無 SDK，且 v1 已足夠驗證產品（決策 R2）|
| 鎖屏 / 背景持續錄音 | 需 Swift 原生層，工期 +1.5~2x（決策 R3）|
| 會議中 AI 出聲 | 回音迴路 + 干擾會議（決策 R4）|
| 帳號系統 / 多租戶 | 單人自用（決策 R5）|
| 會議中即時長出摘要 | prompt 與 token 成本難控，易干擾會議（決策 R5）|
| 視訊 / 螢幕分享記錄 | 與語音記錄是不同產品 |
| 自動發送待辦到外部工具（Notion / Slack）| 依賴外部授權，v1 只做匯出（M02-US-204）|
| 對話框執行**寫入型任務**（建立待辦 / 修改記錄 / 標記）| v1 只讀（決策 D6）；寫入需確認流程 + undo + 權限，做不好會污染知識庫 |
| 對話框執行**對外動作**（寄信 / 建立日曆 / 分享他人）| 與「單人自用 + device token」前提衝突，且發送後無法撤回 |
| 編輯的**版本歷史**（保留舊版文字）| 決策 D7（用戶拍板）：只留 `edited_at` 旗標（D8），不建版本表 |
| 多人共享知識庫 / 協作編輯 | 帳號系統不在 v1（決策 R5）|
| 手動建立概念（v1 只做機器抽取 + 人工修正）| 手動建立成本高且需求未證實 |
