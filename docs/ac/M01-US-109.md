# M01-US-109 AC 範本

> 最後更新: 2026-10-08

## 背景

作為開發者，我需要一個**不依賴網路、可獨立測試**的「逐字稿聚段器」，
把 Deepgram nova-3 串流回傳的**單字層級**結果（含 `speaker` 編號）聚成「一段話」，
以便 M01-US-103（多人即時轉譯）能直接使用，而不需要在網路層裡混著業務規則。

**為什麼這個 US 存在**（SPIKE-001 的結論）：

1. nova-3 的 `diarize` 只在**單字層級**給 `speaker` 編號，SDK 層沒有聚段；
2. `speaker_id` **0 起算**（顯示時才 +1）；
3. 串流**不會**回 `paragraphs` / `utterances`（那是批次 API 才有）→ 聚段規則必須自己寫；
4. `CloseStream` 會掉最後一句 → 必須有 `Finalize` + 明確的收尾（`flush`）；
5. `is_final` 之外的切段訊號只有 `UtteranceEnd`（endpointing）。

**為什麼這是本專案第一個 TDD 標的**：聚段規則是**純函式**（無 I/O、無時鐘、無網路），
是整個 M01 裡唯一能在 5 秒內驗完的核心邏輯；而它一旦寫錯，
錯誤會以「逐字稿句子亂切、講者歸屬跳動」的形式出現在最終產品裡，極難回溯。

## Given / When / Then

> **輸入單位約定**：`start` / `end` 沿用 Deepgram 原生**秒**（浮點）；
> 門檻與輸出用**毫秒**（本產品的正準單位），避免在網路邊界做轉換。

- **AC-1 同一講者連續發言 → 聚成一段**
  **Given** 一串 `speaker` 皆為 `0` 的單字，相鄰字之間停頓皆 ≤ 1200ms
  **When** 餵入聚段器
  **Then** 產出**恰好一段**，`speakerId = 0`、`text` 以單一空格串接
  **And** `startMs` = 首字 `start` 換算毫秒、`endMs` = 末字 `end` 換算毫秒（四捨五入）

- **AC-2 講者變更 → 立即切段（即使停頓很短）**
  **Given** 串流中 `speaker` 由 `0` 變 `1`，且兩字之間停頓僅 100ms
  **When** 餵入聚段器
  **Then** 產出**兩段**，依時間排序、各自 `speakerId` 正確（`0` 然後 `1`）
  **And** `speakerId` **保持 0 起算**，不得自行 +1（顯示層才 +1）

- **AC-3 停頓超過門檻 → 切段（等於門檻不切）**
  **Given** 同一 `speaker`，兩字之間停頓為 1201ms
  **When** 餵入聚段器
  **Then** 產出**兩段**
  **And** 當停頓**恰好等於** 1200ms 時，**不切段**（門檻採嚴格大於）
  **And** 門檻可由選項覆寫（預設 1200ms）

- **AC-4 `UtteranceEnd` 強制收尾，且不吞掉後續字**
  **Given** 緩衝中已有一段未完成內容，且收到 `UtteranceEnd` 訊號
  **When** 之後又送來同一 `speaker`、停頓僅 50ms 的新字
  **Then** 先前的內容成為**獨立一段**（被 `UtteranceEnd` 切開）
  **And** 新字**不得**被丟棄，成為下一段的開始
  **And** 串流結束時呼叫 `flush()` 能取出緩衝中最後一段（對應 SPIKE-001 的
  「`CloseStream` 掉最後一句」）

## 介面契約（實作時發現的關鍵決定）

```ts
feed(event: StreamEvent): TranscriptSegment[]   // 只回「已終結」的段落（0 到多段）
pending(): TranscriptSegment | null             // 進行中的段落（供即時顯示）
flush(): TranscriptSegment | null               // 串流結束時取出最後一段（冪等）
```

**為什麼 `feed()` 不回傳「最後一段」**：串流中最後一段在**下一個字到來前無法判定是否完成**
（下一字可能是同講者續講）。提早吐出＝製造「句子亂切」——這正是本 US 要防的失敗模式。
因此契約是：終結訊號（講者變更 / 停頓超標 / `UtteranceEnd` / `flush`）才產出段落。

> 這條決定是 **TDD 第一輪紅燈逼出來的**：初版測試假設「餵入即得段落」，
> 實作跑出 0 段 → 發現是測試的假設錯了（批次語意），不是實作錯了。
> 修正的是**測試與 AC 的措辭**，並把契約明寫進本節（避免下一個實作者重蹈）。

**前置條件（餵入者的責任）**：本聚段器**假設餵入的是已去重的 `is_final` 單字**，
且 `UtteranceEnd` 必須在**該句的 final 結果落地之後**才餵入。違反任一條會產生重複段落：

- 若把 interim 結果也餵進來 → 同一字被推入兩次 → 文字重複；
- 若 `UtteranceEnd` 先到、該句 final 遲到 → 先吐出一段「部分內容」，稍後又產生一段。

這不是聚段器的邏輯錯（它只是照契約工作），而是**整合層的職責** →
已寫進 `M01-US-103` 的 AC-6（同段不得重複產生）。由 Gate 4 reviewer 指出。

**誰是主要切點（Gate 4 發現的真實不一致）**：SPIKE-001 實測的串流參數是
`utterance_end_ms=1000`（見 `docs/spike/SPIKE-001.md` L35），
而停頓規則的預設門檻是 1200ms → **實務上 `UtteranceEnd` 會先觸發（約 1.0 秒靜音）**，
所以實際段落邊界 ≈ 1.0 秒，1200ms 規則只是**後備**（用在 `UTTERANCE_END` 事件沒送達時）。
兩者不需強制相等，但**文件必須說清楚**，否則會出現「設計寫 1.2 秒、行為是 1.0 秒」的落差。

**浮點陷阱**：Deepgram 以秒回傳浮點，`2.2 - 1.0 = 1.2000000000000002` 秒。
若直接比 `> 1.2` 會把「恰好 1200ms」誤判為切點 → 故先 `Math.round(gapMs)` 再比，
讓「等於門檻不切」的語意可靠（AC-3 有專門測試）。

## 邊界與例外

- 輸入空陣列 → 回傳空陣列（不得產生空段）
- 只有一個字 → 回傳一段
- `punctuated_word` 存在時優先使用（保留標點與大小寫），否則用 `word`
- 輸入不得被修改（不得就地排序或變更原物件）
- 聚段器**無時鐘**：所有判斷只依輸入的 `start` / `end`，同樣輸入必得同樣輸出
