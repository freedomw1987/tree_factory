# M01-US-108 AC 範本

> 對應 Backlog: [M01-US-108 in docs/backlog.md](../backlog.md)
> Module: M01（聽：收音與即時逐字稿）
> 最後更新: 2026-10-09

## 背景

作為會議參與者，我想在錄音期間**螢幕不要自己關掉**，
以免我什麼都沒做、錄音卻因為裝置休眠而中斷。

這一票是 **US-107 的搭檔**：US-107 負責「斷了要誠實說」，
US-108 負責「不要讓它白白斷掉」——用 Web 標準 `navigator.wakeLock`（`screen`）在錄音期間抑制自動關屏。

三個必須誠實處理的現實：

1. **WakeLock 進背景就會被系統沒收**，而且回來不會自己回來 → 必須在回到前景且仍在錄音時**重新取得**。
2. **它不是每一台裝置都有、也不是每一次都給**（省電模式會拒絕）→ 拿不到時必須明說「請保持畫面開啟」，
   而不是顯示一個假的「已防止關屏」。
3. **鎖屏是使用者的自由**：就算 WakeLock 生效，他按下電源鍵仍會中斷 → 這時由 US-107 的缺口列接手。

## Given / When / Then

- **Given** 會議正在錄音
  **When** 錄音開始（或從中斷恢復成錄音中）
  **Then** 主動取得 `screen` wake lock，並在**回到前景時自動重新取得**（因為進背景已被系統釋放）
  **And** 會議結束／2 小時上限關閉／回到中斷狀態時必須釋放，不得繼續宣稱螢幕受保護

- **Given** 裝置不支援 WakeLock，或系統拒絕（例如省電模式）
  **When** 會議中
  **Then** 畫面顯示「請保持畫面開啟」的提示，說明離開畫面會中斷錄音（誠實說明，不假裝已防護）
  **And** 若 WakeLock 曾取得，且**在可見（前景）狀態下**被系統釋放（低電量／系統省電策略），提示必須在同一場會議內重新出現
  **And** 真機按電源鍵是「系統釋放 sentinel ＋ 頁面變 hidden」幾乎同時發生，而兩者的先後無保證：
  兩種順序都不得宣稱螢幕仍受保護、也不得因此多打註定失敗的請求（最多初始 1 + 重試 1），但**落點可以不同**、
  且兩種落點都必須與真實狀態一致：
  - 若 `hidden` 先到（我方已主動收乾淨）→ 停在「已暫停、不給提示」（誠實訊息由 US-107 缺口列負責，
  因為那一刻錄音已中斷，再喊「請保持畫面開啟」反而是在說一個使用者已經知道的錯方向）；
  - 若 `release` 先到、而瀏覽器當下已非前景（重取必被拒）→ 停在「已失去」並顯示提示
  （真的沒有保護就該說，不得停在無提示的狀態）。
  回前景且真的續錄時，兩種情況都必須恢復到「已保護」且清掉提示。
  **And** 重試有上限（連續失敗達上限就停，成功即歸零；不無限重打註定失敗的請求），失敗後停在「已失去」並持續顯示提示

## DoD（Definition of Done）

- [x] 成功／不支援／被拒絕／被釋放 四種狀態都可在畫面上區分（`data-wakelock-state`），並且都測得到
- [x] `request()` 的失敗不會變成 unhandled promise rejection（一律 catch 並轉成狀態）
- [x] 「重新取得」有明確上限（**連續失敗**達上限就停在「已失去」，取得成功即歸零；避免與 US-107 的永久失敗同類的無限重試）
- [x] 取得失敗一律有明確狀態與提示：連「請求卡住不回來」也要在逾時後誠實降級顯示提示，不得停在無提示的狀態（靜默無保護）
- [x] 探針含正向（錄音 → 取得）與負向（不支援 / 被拒絕 / **中斷後回前景不得重新取得**）兩類斷言
- [x] `REGRESSION_MODULE=M01` 全綠

## 範圍外（明確不做，避免膨脹）

- **真的背景／鎖屏續錄**：US-106 原生錄音層（本票只防「螢幕自動關」，不防「使用者主動鎖屏」）。
- **推播提醒使用者回前景**：SPIKE-002 實測 `Notification` 在 Tauri webview 不可用 → 不在本票。
- **WakeLock 以外的省電策略**（例如靜音播放無聲音檔維持前景）：未經實測，不做。
