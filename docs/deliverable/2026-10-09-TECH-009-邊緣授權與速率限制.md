## 1. 這一票到底解決了什麼

`worker/src/index.ts` 原本只比對 pathname 就把請求轉進 Durable Object——**沒有任何認證**。
`worker/src/cors.ts` 決定的是「瀏覽器讀不讀得到回應」，**不決定要不要處理**：不在白名單的來源
照樣進 DO、照樣寫資料。而 `GET /m/:id/wake`（`meeting-do.ts:171-207`）與 `GET /m/:id/release`
是**會改狀態的 simple request**，simple request 不觸發 preflight，
所以任何網站的 `<img src="https://…/m/x/wake?ms=0">` 都能讓它成真——**不需要讀到任何東西就能造成副作用**。

這一票在「進 DO 之前」立三道關，順序是**先問來源、再問憑證、最後問額度**：

1. **`Origin` 關**：不在允許清單 → `403 ORIGIN_FORBIDDEN`，**副作用不發生**（修好「擋了讀取、但照樣執行」）。
2. **憑證關**：`Authorization: Bearer <DEVICE_TOKEN>`；沒設定憑證 → `500 AUTH_NOT_CONFIGURED`（**fail-closed**，
   刻意沒有「沒設就放行」的開發模式）；憑證錯 → `401 AUTH_INVALID`。**順序在 `Origin` 之後**，
   所以 403 不會洩漏「你猜的 token 對不對」。
3. **速率限制關**：同一 `token 指紋 + client IP` 在 60 秒窗內超過 300 次 → `429 RATE_LIMITED` + `Retry-After`。

再加上第四件（票沒點名、但同一個洞的形狀）：**會改狀態的端點一起改成只收 `POST`**——
`/wake`、`/release`、`/session/start`、`/session/stop` 四條收斂成 `POST_ONLY_PATHS`，
判準是「**不必帶 body 就能改狀態**」。只修 `/wake` 等於修一半：`<img src="…/release">` 能讓裝置端
停止保護，`<img src="…/session/start">` 能替對方開一場會議（真 workerd 實測第 1 輪是 **201 Created**——
這是 Gate 4 第 1 輪 reviewer **P2-2** 抓到的，不是我自己看出來的）。

裝置端配套（AC-6）：`HttpSessionClient` 有 token 才送標頭；`401` 的文案改成
「裝置授權已失效，請重新配對」（不再叫人去查一條沒壞的網路線）；建置期沒設 `VITE_DEVICE_TOKEN`
就**不送**標頭（`deviceTokenFrom` 不得退化成任何內建預設值）。

**範圍**：worker 3 支新檔（`edge-auth.ts` / `rate-limit.ts` + 3 支測試）、6 支改檔；app 6 支改檔 + 3 支測試；
E2E 新增 1 支（3 條）+ 1 支共用模組；文件 5 份（含兩張錯誤碼表同步）。
**審查**：Gate 4 兩輪（第 1 輪 oracle「可合併」／reviewer「需修正後合併」，第 2 輪見 §5）。

平台 Rate limiting rules、任何「沒設 token 就放行」的開發開關、依 `Retry-After` 微調退避、
把 token 放進 query string 或 body。

## 8. §2.4 反思（六維度）

### 1. 這一次做得好的地方

**把「閘門順序」當成規格、而不是實作細節**。設計階段就寫死
`Origin → 憑證 → 額度 → 進 DO`（D3），因此有兩件事變得很便宜：
突變 W26（把順序對調）能夠被一條測試殺死，而且**403 不洩漏 token 對不對**這件事
不需要另外設計——它是順序的直接結果。

**先問「誰會踩到」再寫程式**。`/release` 是票沒點名的，但它與 `/wake` 同形狀：
一開始的判斷是「只修一半等於沒修」，所以擴大處理並在交付文標明。事後看，
如果只修 `/wake`，這一票的價值會被砍半（`<img src="…/release">` 仍能讓裝置端停止保護）。

**證據自己講話**：突變表格是腳本印的、E2E 守門測試是**先紅才修好**的。這輪抓到的最有價值
東西（UI 4 個呼叫點只有 1 個帶 token）不是靠讀碼看出來的，是靠「UI 自己發出的每一個 `/m/` 請求
都帶了裝置憑證」這條自動化斷言逼出來的。

### 2. 做得不好的地方

**第一輪突變有兩條存活，代表測試一開始不夠硬**。W25（`Retry-After` 用固定窗長）與
W34（空字串 token 也能過）都是我以為「測過了」的格子。**教訓**：寫完測試要立刻問
「這一條如果把實作換成我最懶的寫法，它會不會還綠？」——W25 這種「數值語意」型的格子
（不是「有沒有」，而是「多少」）特別容易只驗存在性。

**`classifyFailure` 用 duck-typing（`typeof error.status === "number"`）**：當下是為了
不讓 UI 端 import worker 的錯誤類別，但代價是「任何帶 `status` 的錯誤」都會被當成伺服端拒絕。
現在靠 `NotAllowedError`/`SecurityError` 先被攔下來撐住，但這是**順序相依**的脆弱設計。
正確做法是把「有哪些錯誤會往上拋」寫成 UI 端自己的聯合型別。

**「同一個形狀」的路由我一開始是逐條點名，而不是寫成規則**。第一版只把 `/wake` 與 `/release`
改成 POST-only（票只點名 `/wake`，我多修了一條就以為想到了）；Gate 4 第 1 輪 reviewer **P2-2**
指出 `/session/start` 同一個形狀（不必帶 body 就能改狀態）卻沒守——真 workerd 上 `GET /session/start`
回 **201**。修法不是「再點一條名」，而是把判準寫成常數
（`POST_ONLY_PATHS` ＋「不必帶 body 就能改狀態」），並用突變 **W43**（退回兩條）證明新測試有牙齒。
**教訓：清單會漏，規則不會——當你發現自己在「再補一條」，就該問「這條的判準是什麼」。**

**`docs/` 與 `worker/` 的 markdownlint 檔數從 78 變 82（含 TECH-014 的兩份文件），但沒有一條檢查在守「設計文件
新增後，錯誤碼表的兩份文件是否一致」**。這次是我手動對的（13 vs 13）。

### 3. 學到的（寫給下一票的自己）

- **「順序」是可測的規格**。凡是「A 先於 B」的敘述，都要有一條測試讓它紅。
- **認證這種橫向關注點，最容易死在「呼叫點不只一個」**。這輪的實際 bug 就是 4 個
  `new HttpSessionClient(` 裡只有 1 個帶 token——**橫向改動一定要有「全稱斷言」**
  （「**每一個**請求都帶了」），而不是逐點檢查。
- **fail-closed 不是形容詞，是要能看到 500 的**。`DEVICE_TOKEN` 空字串時全部 500，
  這條在真 workerd 上驗過，比任何註解都有用。
- **`.dev.vars` / secret / 建置期 env 是三種不同的東西**：這一票把三者寫進
  `docs/env-setup.md §6`，以後不用再猜「為什麼我本機可以、CI 不行」。

### 4. 測試的層次：這一票值錢的是「真 workerd 上的三關順序」

最有鑑別力的一條是**故意用不合法的方法 + 不帶憑證**打 `PUT /wake`：
如果閘門順序寫反（方法關先於憑證關），它會回 405；回 401 才代表「先問身分、再問方法」。
這種「兩關互相掩蓋」的情況，只有真環境實測才會露出。單元測試兩邊都綠也可能順序是錯的
——因為兩關各自都測到了。

### 5. 品質與速度

TECH-009 從設計到綠燈約 2 小時（含 42 個突變、兩顆真 workerd 的冒煙、E2E 55 條），
仍在 trust mode 的預算內。代價是**文件回寫 3 份**（`system-design.md`、`DESIGN.md`、`env-setup.md`），
都是票裡已經寫成規則的事（新錯誤碼必須同步兩張表），所以不算意外。

### 6. 對 Backlog 的影響（下一票的輸入）

- TECH-009 這一格（P1 / 3 SP）可以關掉。
- 這一票顯化了三件**應該進 backlog** 的事（尚未開票，留給使用者決定）：
  1. **真機 `Origin` 實測**（Tauri／WKWebView）—— 與 TECH-006 同一個缺口，是上真機前的阻斷項。
  2. **`Retry-After` 接入 `uploader.ts` 的退避**（現況：窗可能 60 秒、退避上限 30 秒）。
  3. **平台層 Rate limiting rules**（與 TECH-003 共用同一個憑證阻塞）。
- **新增的教訓**：任何「橫向關注點」（認證、CORS、時鐘、上限）都要有一條
  **全稱斷言** 的測試（「每一個請求都…」），否則漏掉的呼叫點不會有任何症狀。
