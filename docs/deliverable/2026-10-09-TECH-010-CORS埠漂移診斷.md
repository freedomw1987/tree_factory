# 交付：TECH-010 — CORS 埠漂移的診斷標頭與重播腳本

- 票號：TECH-010（P2 / 1 SP）｜模組：—（worker 側）｜日期：2026-10-09
- AC：`docs/ac/TECH-010.md`｜設計：`docs/design/TECH-010-cors-diagnostic-headers.md`
- 前置：TECH-006（`DEBUG_ORIGINS=1` 的事件記錄）
- 執行方式：trust mode（自主 SOP），無中途提問

## 1. 這一票到底解決了什麼

**問題**：dev server 埠漂移（1420 → 1421）時，worker 的白名單沒中 → 瀏覽器把回應整包擋掉 →
前端只看到 `Failed to fetch`，**與「請求根本沒送到」完全同症狀**。
TECH-006 已經把證據寫進 server log（`[cors] allowed=false`），但開發者的第一現場是 DevTools，
而且 CORS 失敗時 JS 讀不到 body——**唯一還留在現場的是回應標頭**。

**做法**：

1. `worker/src/cors.ts` 新增 `corsDiagnosticHeaders(origin, configured, debugFlag)`：
   在 `DEBUG_ORIGINS=1` 時回傳 `x-cors-origin`（對方送的來源，沒帶則 `(none)`）
   與 `x-cors-allowed`（`true`/`false`）；未開旗標時回空物件。
   `withDiagnostics(response, headers)` 把標頭併上去，**空 map 時原樣回傳同一個 Response**。
2. `worker/src/index.ts` 在入口計算一次，套用到**三條**回傳路徑：
   `OPTIONS` preflight、首頁路由清單、DO 轉發結果。
3. `worker/scripts/cors-probe.mjs`：把「curl 手動重播」寫成腳本——
   同一個 worker、同一組 `Origin`，依序送 OPTIONS 與 POST，印出 status 與
   `access-control-allow-origin` / `x-cors-allowed`。

**這一票沒有解決的**（見 §4）：前端 JS **仍然讀不到**這些標頭（CORS 失敗時 `fetch` 直接 reject）；
「同症狀」是**降級**（從「兩邊都看不出來」變成「DevTools 一眼可辨」），不是消滅。

## 4. 誠實聲明：**沒有**被驗到／做不到的部分

1. **前端程式仍然無法自動分辨。** CORS 失敗時瀏覽器的 `fetch` 直接 reject、`response.headers` 不存在，
   所以 JS 拿不到這兩個標頭。這一票的受益者是**開發者**（DevTools），不是裝置端程式。
2. **真的 webview（Tauri / iOS WKWebView）沒跑。** 腳本重播的是 wire（同一 worker、同一 `Origin`）；
   webview 的 scheme 差異正是 TECH-006 的產物，仍需人跑一次。本票**沒有**新增 webview 實測。
3. **正式環境仍只能靠 log 或主動探測。** 診斷標頭只在 `DEBUG_ORIGINS=1` 時出現（刻意的零足跡取捨）。
   正式環境若 `ALLOWED_ORIGINS` 設錯，`cors-probe.mjs` 可用但只會顯示「未開旗標」＋有無允許標頭。
4. **`x-cors-origin` 是回顯對方輸入（已淨化，但仍非萬能）。** Gate 4 oracle 用 raw socket 實測：
   workerd 會擋掉含 CR/LF（obs-fold）與 NUL 的請求（`400`），但**垂直 tab `0x0B` 會被原樣寫進回應標頭**。
   處置：`safeHeaderOrigin` 只放行可見 ASCII（`\x20`–`\x7e`，≤255），其餘回 `(invalid)`（真 workerd 已驗）。
   **殘留**：`(invalid)` **不是**對方原文，所以標頭只是「診斷用副本」；且同一個測試方法只跑過
   curl / raw socket / node fetch 三種客戶端，其他客戶端未窮舉。
5. **`cors-probe.mjs` 用文字解析 `src/cors.ts`。** 若 `DEV_ORIGINS` 的宣告形式改了（例如改成從配置檔讀），
   解析會失敗 → 腳本 exit 2 並提示「清單搬家了」。這是刻意的（寧可吵鬧，不要偷偷用一份過期清單）；
   而「解析到區塊卻 0 筆」原本會靜默退化成只剩漂移對照組（oracle P2-3），現已改成明確報錯。
6. **沒有自動化 webview 流程。** TECH-010 的原票敘述有「webview 實測流程腳本化」；
   本票只腳本化了 **wire 重播**這一半，webview 那一半仍待（已在 AC 與本節明列）。
7. **`withDiagnostics` 對串流 body 的影響沒有實測。** 它與既有的 `withCors` 一樣用
   `new Response(response.body, …)` 重建；能打到的 DO 路徑全部回非串流（204/200/201/400/404/405/409），
   真的 SSE/long-poll 是否仍即時 flush 未驗（oracle 也列為未驗項）。
8. **`scripts/**` 仍然不在 `tsconfig` 的 `include` 內。** P1 的修法是「把判斷邏輯抽出來測」，
   不是「讓 typecheck 涵蓋腳本」——`cors-probe.mjs` 的 IO 部分（fetch、讀檔、印字）仍只有實跑證據。

## 6. §2.4 反思（六維度）

1. **目標達成**：AC-1~AC-8 都有單元測試 + 真 workerd 證據；「埠漂移」從不可分辨變成
   DevTools 可分辨、CLI 可重播。**但縮小了原票敘述**（webview 那一半沒做），已在 §4 明列。
   本輪最大的價值不在功能，而在**把一條「看起來有驗、其實沒守」的驗收條件補起來**（見第 2 點）。
2. **測試品質**：新增 17 條（純函式 7、合併 4、入口 6）＋ `cors-probe-lib.test.mjs` 11 條。
   純函式用 `toEqual` 精確比對（不是「有就好」）；入口層覆蓋 preflight / POST / 首頁 / 未開旗標。
   **最重要的一課**：送審時 AC-5 把「離開碼 0/1/2」寫成驗收條件，但那套邏輯在 `.mjs` 裡、
   殺不死任何測試——oracle 的 M5 把它變成全綠假象。修法不是補文字，而是**拆檔讓它可測**。
   8 條突變全部有紅燈（M5 由 0 紅變 5 紅），基線 43 綠。殘留：入口層用假 namespace；
   真 workerd **沒有**斷言「未開旗標時零診斷標頭」——這條只有單元測試（§4 已記）。
3. **設計品質**：D1~D9 每條都寫了可推翻條件；四個「不做」的理由是安全與假陰性（不是省工）。
   D7/D8 是**被審查逼出來的**：兩個都不是 bug 報告，而是「你這票新開的攻擊面／快取面」——
   這說明對抗通道的價值在於它會問「## 你新加了什麼」，不只是「你的程式對不對」。
   已知弱點：旗標與 TECH-006 共用，若有人把 `DEBUG_ORIGINS` 當成「只在 log 用」，
   會意外多送標頭——但這是 dev-only 旗標，代價可接受。
4. **文件與事實一致**：AC 的「誠實範圍界定」與 §4 是這一票最重要的產物——
   它把「同症狀沒有被消滅，只是降級」寫死，避免下一個人以為前端能自動判斷。
5. **流程品質**：Gate 1 紅燈數字（`10 failed | 15 passed (25)`）與綠燈數字都留著；
   真 workerd 用了三顆 wrangler（8807 開旗標、8808 不開、8809 重構後）拿到正反與回歸證據。
   **踩到的坑記在案**：①三顆 wrangler 不能並行（`bind(): Address already in use`，os error 48）；
   ②wrangler 熱重載會在檔案改動後**短時間內供應舊建置**（oracle 因此一度誤判不變式失效）；
   ③重構 `cors-probe.mjs` 後 `node --check` 不會抓「重複宣告」——**真跑一次**才發現
   （原本會 `SyntaxError: Identifier 'base' has already been declared`）。
6. **殘留風險**（轉票候選）：
