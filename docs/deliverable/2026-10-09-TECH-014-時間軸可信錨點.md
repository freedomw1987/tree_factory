## 0. 一句話結論

> **session 的「開始 / 結束」兩個時間欄現在有一個外部金鑰簽的 HMAC 戳記。**
> 攻擊者就算能在 SQLite 裡自由改 `meeting_session.started_at_ms` / `ends_at_ms`，
> 只要改了，讀的時候 HMAC 對不上就 500 SESSION_CORRUPT——「同量平移讓上限被續命」
> 這條已知漏洞（Tech-008 結案時釘下的樁）正式被收緊。

---

## 1. 為什麼這件事值得做

Tech-008（時間合理性檢查）留了一個**已知限制**（當時刻意不做）：
「同量平移」可放行——「已錄 1 小時、平移 1 小時」會被視為「剛好上限 1 小時」，
攻擊者拿這個漏洞可以**無限續命**已過期的會議。

Tech-014 補完這條：「無論位置檢查怎麼說，**外部金鑰**對 DB 內容的『三元組』
（meeting id + 開始時間 + 結束時間）簽的 HMAC 必須對得上。對不上 = SESSION_CORRUPT」。

代價（**接受範圍內**）：
- 多一個 secret（`SESSION_ANCHOR_KEY`）
- 沒設金鑰時**不能開新會議**（fail-closed）
- 金鑰換掉後**既有會議全炸**（v1 不做平滑輪替期；見 §6）

## 4. 設計的「為什麼」（給未來讀者）

### 4.1 為什麼同步閘門 + 同步快取 `#anchorGateSync`

Tech-008 / Tech-013 在 `#readSession` 內部保留了**「read → gate → write」原子不變式**
（line 781 附近）。如果在這條路徑上加 await，
會被 microtask 打斷——這條不變式就破了。

**解法**：「甦醒時算一次」+「讀取時同步比對」。**`#anchorReady` 的結果在 `fetch` / `alarm`
開頭 await 過了，但 `#readSession` 在它**後面**的同步路徑上仍要能讀到**——所以
**同時寫進 `#anchorGateSync` 這個**非 promise 欄位**。** 同步路徑讀 `#anchorGateSync`
而不是 await `#anchorReady`。

> 這是**唯一**不拆 read → gate → write 原子性，又能讓 Tech-014 同步閘門生效的設計。

### 4.2 為什麼 `#anchorReady` 永不 reject

`#anchorReady` 是**「甦醒後讀到的資料是否合法」**的描述，不是例外。
如果 reject，`fetch` / `alarm` 開頭的 `await this.#anchorReady` 會整條拋出去——把
「壞資料」變成「系統崩潰」。壞資料是資料，**該走 SESSION_CORRUPT 500**。

### 4.3 為什麼「unchecked」是一個**第三態**（不是 true / false）

設計 D6 寫得很清楚：**未設金鑰 = 不能開新會議**（fail-closed）。但**既有的、未錨定的 session
仍可讀**——這是讓測試 / 開發能「先看」現有資料的權宜，且符合「壞資料是資料、不是崩潰」。

### 4.4 為什麼 `write()` 不自動寫錨

`SessionStore.write` 是**純儲存動作**（接 SQL）。**`anchorMac` 帶金鑰**，金鑰在 `env` 裡、
不在 store 裡。把金鑰塞進 store 等於讓 store 變成「知道祕密的通用物件」——這條
越界很常見於日後重構。

**現在的設計**：`#sessionStartRoute` 是**唯一**同時擁有 `env` 與 store 兩者的點——
它在 `write` 之後顯式呼叫 `writeAnchor`。**寫錨是 route 的責任，不是 store 的責任。**
