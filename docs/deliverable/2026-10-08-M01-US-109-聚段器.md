## 摘要

把 SPIKE-001 的設計結論落成**可測的產品代碼**：`TranscriptSegmenter`——
把 Deepgram nova-3 串流的**單字層級**結果（含 `speaker`）聚成「一段話」。
純邏輯、無網路、無時鐘，17 個測試全綠；並補上專案第一個 Gate 3 探針執行器
（`REGRESSION_MODE` + Module 前綴 + JSON 報告）。

過程中由**第一輪紅燈**逼出一個真實的契約問題：`feed()` 該不該回傳「最後一段」——
答案是不該（串流中最後一段在下一字到來前無法判定完成，提早吐出就是「句子亂切」），
契約因此明寫進 AC 文件。

   Deepgram WS 連線、`Finalize` / `CloseStream` 的實際呼叫、`UtteranceEnd` 訊息的解析
   仍屬 M01-US-103 的範圍（TECH-003 是同族的環境票）。
2. **`is_final` 的重送與事件順序未在代碼內防護**（Gate 4 reviewer 指出）：
   目前**以契約承擔**——聚段器假設餵入的是已去重的 `is_final`，且 `UtteranceEnd` 在該句 final 之後。
   若上游違反，會產生重複段落。已在 AC 文件明寫前置條件，並把防護責任交給
   **M01-US-103 的 AC-6 / AC-7**（本輪補上）；若要更保險，可讓 `TranscriptSegmenter`
   自己依 `idempotency_key` 去重（屬 M01-US-103 的設計選擇，屆時再決定）。
3. **沒有跑前端回歸**：本次未動任何前端檔案，故未重跑 125 狀態原型驗證器

### 根因分析與改善動作

| 問題 | 根因 | 改善動作 |
| --- | --- | --- |
| 初版測試假設批次語意 | 寫測試時想的是「一天結束後驗資料」，不是「串流中每字到來時的狀態」 | 已把契約明寫進 AC 文件「介面契約」節；**教訓：串流元件的測試必須以「事件序列」為單位寫** |
| `is_final` 重送未處理 | 聚段器被設計成「信任上游去重」但沒把這個假設寫下來 | 已把前置條件寫進 AC 文件；M01-US-103 補 AC-6 / AC-7 |
| **契約只寫了「語意」沒寫「前提」** | 寫 AC 時想的是「這個函式做什麼」，沒寫「我假設上游怎麼餵我」——**契約的一半被漏掉了** | 已在 AC 文件新增「前置條件」段落（feeder 的責任）。**教訓：純函式的契約＝語意 + 前提 + 不變量，三者缺一** |
| Gate 3 執行器會「0 測試假綠」 | 只看 exit code，沒檢查「真的跑了幾個測試」 | 已加 `passed > 0`（此類假綠是自動化最危險的失敗模式） |
