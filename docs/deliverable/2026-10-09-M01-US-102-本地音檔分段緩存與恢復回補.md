# M01-US-102 交付：本地音檔分段緩存與恢復回補

- **Ticket**：M01-US-102（8 SP，P0）｜Module M01（聽：收音與即時逐字稿）
- **AC**：[docs/ac/M01-US-102.md](../ac/M01-US-102.md)｜**Design**：[docs/design/M01-US-102-audio-chunk-idempotency.md](../design/M01-US-102-audio-chunk-idempotency.md)
- **交付日期**：2026-10-09（trust mode，SOP v2.0 全流程）
- **一句話**：錄音每 30 秒落地一段可獨立回補的音檔；送不出去的留在本機，重開 app 會**問使用者**要不要續傳，並以伺服端帳本為準只補缺、不重複、不覆蓋。

## 1. 這一票到底解決了什麼

斷網或 app 被殺之後，如果音檔只存在記憶體，整場會議就報廢了。本票把「收音」改成
**30 秒一段、每段獨立可解碼、上傳成功才刪**，並加上兩層真相來源：

| 層 | 誰是權威 | 為什麼 |
| -- | -------- | ------ |
| 分段與時間軸 | 裝置端 `seq`（單調遞增） | 只有裝置端知道「我錄了哪幾段」 |
| 已確認收下 | 伺服端帳本（`GET /audio/chunks`） | 只有伺服端知道「我真的收到了」 |

兩者對帳（不是看誰的旗標比較新）是 AC-2「不重複送已確認的分段」與 AC-4「無缺段」的實作方式。

## 4. 誠實聲明：**沒有**被驗到的部分

1. **沒有在真機上真的把 app 殺掉**。E2E 用 IndexedDB 跨頁面載入（`page.reload()`）代替程序重啟——
   資料面等價（新的 `ChunkRecovery` 面對同一份磁碟狀態），但「iOS 在低記憶體下真的會 flush IndexedDB 嗎」
   屬於平台行為，本票沒有真機證據。**建議**：TECH-006 的真機驗收流程加一條「錄音中強制終止 → 重開 → 應出現恢復畫面」。
2. **沒有真的 STT**。worker 在測試環境跑 `HARNESS_PROVIDER:faux`，所以「無重複句」是在**帳本／逐字稿寫入層**
   驗的（同 `chunkSeq` 兩次 → duplicate），不是拿真 ASR 的輸出比對。
3. **分段邊界 <100ms 的縫隙沒有量測**。MediaRecorder 的 stop/start 之間留著極短的音訊空洞，
   目前只保證「每段可獨立解碼、順序正確」，沒有做「把段拼回單一檔後聽起來連續」的驗證。
4. **本機刪除只在 flush 的對帳路徑發生**，目前沒有「儲存空間不足」的處理（設計 §6 只承諾明說「沒有本地備份」）。
5. **`ContentMismatch` 的復原出口還沒做**：同 seq 不同內容時我們保留本機檔並回報衝突，
   但使用者除了「丟棄」以外沒有別的選擇（要人工判斷哪一份是真的）。

## 6. §2.4 反思（六維度）

### 1. 這一票做得好的地方
- 「先落地才送出」與「伺服端帳本是權威」兩個決定，讓 AC-2/AC-3 從「靠旗標猜」變成「靠對帳算」，
  之後要加匯出、斷點續傳、多場同時恢復都不必改核心。
- 把管線邏輯抽成純 `.ts`（`chunk-pipeline.ts`）而不是塞進 `app.svelte.ts`：rune 需要編譯、難單測，
  抽出來之後這一票的所有核心行為都能在毫秒級單元測試裡重跑。

### 2. 最大的失誤：把「問題」寫進註解卻沒寫成測試
F1 的歸零行是我上一輪加的，當時還留了「這裡是新的生命週期」的想法——它讀起來合理，但没有任何測試會抗議。
**教訓**：只要一句話聽起來像「這裡應該不會怎樣」，它就需要一條會紅的探針。這一輪補的兩條探針
（seq 續接、startedAtMs）都是這種句子。

### 3. 為什麼審查抓得到、我自己沒抓到
我做的是「AC 逐條對照」，審查做的是「跨 AC 交互」——AC-4（背景中斷續錄）與 AC-1（seq 單調）的**交集**就是 F1 死點。
以後自審要加一句：「這張票的哪兩個 AC 碰在一起？」。

### 4. 測試的層次補齊
原本只有單元測試（續傳邏輯）與「丟棄」的 E2E，缺的是**續傳**的 E2E。補了之後才發現一個真實的測試設計缺陷：
wrangler dev 的 DO 狀態會留在 `.wrangler/state`，用固定會議 id 會讓第二次跑變成「內容衝突」——
那反而變成一條免費的 F4 證據。教訓：**測試要能在「之前跑過」的環境上重跑**。

### 5. 品質與速度的取捨
信任模式下我選擇把 7 條審查意見一次做完（含 P2），代價是這一票多花了時間；但 F1 是**靜默丟音**，
P2 的 F4/F7 也都是「使用者會以為資料在、其實不在」的同一類傷害。這一類的 P2 不該延後。
