## 1. 這一票到底解決了什麼

`POST /transcript` 從 US-101 起就寫著「逐字稿內容的落地由 M01-US-103 接上」——
也就是說，**會議中講的每一句話從來沒有被存下來過**，只被計數。這一票把那個洞補上，
並且回答三個問題：**誰說的**（speaker 編號）、**什麼時候說的**（毫秒時間戳）、**重送會不會變成兩句**（不重不漏）。

三個現實決定了這一票的長相：

- **上游給的是原始事件，不是句子**。Deepgram nova-3 的 WS 回的是 `Results` / `UtteranceEnd` / `SpeechStarted`，
  字詞散在 `channel.alternatives[0].words` 裡（秒為單位、每個字帶 `speaker`）。
  所以先補一層**純函式翻譯**（`nova-events.ts`），再接 US-109 既有的聚段器。
- **「誰說的」不能交給裝置端決定**。同一段音訊在兩台裝置上若各自切句，會有兩種答案。
  切句（speaker 切換 / 停頓 / `UtteranceEnd`）放在**伺服端**，重播同一份事件串流得到的段落逐字相同。
- **串流就是會重送**。斷線重連、上游重播、裝置重試都會讓同一句再來一次；
  身分鍵用「**同一個人 + 同一個起點**」（`seg:<speakerId>:<startMs>`），重送收斂成 `duplicate`、
  不新增列、不改寫既有句子（append-only）。內容真的不同的同鍵請求**不靜默覆蓋**，
  而是回報 `conflict` 並附上兩份全文。

## 6. §2.4 反思（六維度）

### 1. 這一票做得好的地方：把「真跡」當唯一真相來源

這一票所有的關鍵數字都不是我「覺得」，而是從 `spike/results/spike-001-ws-diarize.json`
（SPIKE-001 那次真的連上 nova-3 收到的 38 則訊息）**重播**出來的：6 段、speaker `0/1/0/1/0/1`、
242 個字詞一字不丟、66 個 final 字詞。連「interim 是累積式重送」這種會決定顯示品質的行為，
也是從真跡 24 則 interim 一則一則比對出來的（第一版顯示緩衝就是被這個實測推翻的）。
**真跡在手，才敢說「我不知道」**——例如「真跡裡 0 則 `UtteranceEnd`」這件事讓我在文件裡明講
AC-7 的證據是合成事件，而不是含糊帶過。

第二件做對的是**把不確定的地方變成「契約 + 釘樁測試 + 票」**，而不是偷偷繞過（見 §5 的 P0-1）。

### 2. 最大的失誤：我的探針有兩次是**假的**，而且我自己沒看出來

第一輪 I 用「改壞程式看測試紅不紅」檢查探針品質，結果**兩條突變活了下來**：

- M2 我把突變寫成「在既有的 `&&` 鏈前面加 `true &&`」——**那是一個空操作**（等價重寫），
  測試當然全綠。我一度以為「測試太弱」，真相是**我的突變根本沒改行為**。
- M5 我把「重送也計數」改壞後，測試竟然還是綠——因為那條斷言剛好是
  `0 accepted + 1 duplicate = 1`，**與正確值撞在同一個數字上**。

兩者都不是「測試不夠多」，而是**探針沒有辨別性**。修法也不是加一堆測試，而是：
M2 改成真正改變回傳值；M5 補一條會把正確值與突變值分開的測試（寫一列 → 重送 → 再寫新的一列 → 必須是 2，突變後變 3）。
**教訓：突變存活時，先懷疑突變，再懷疑測試。** 這句話我會帶進下一票。

第三個失誤是**文件寫了錯的數字**：第一版 design 寫「7 則 final 收斂成 6 段」與
「nova-3 該次回的是 `speech_final`」，實際上 31 則 `Results` 的 `speech_final` **全是 false**，
而 7 → 6 的真正原因是**一則空 final 被丟棄**（段落邊界與 final 邊界其實**不重合**）。
這些是 Gate 4 的兩條通道各自抓出來的——**如果沒有第二條獨立通道，錯誤的說明會直接進 main**。

### 3. P0-1 的取捨：我選了便宜但誠實的路

oracle 的 P0 是對的：`/transcript/stream` 的聚段緩衝活在**單一請求**裡，所以「同一場會議拆成多個請求」
會**靜默少字**（實測 66 字 → 28 字，而且沒有任何錯誤回報）。我選了 (B)「文件契約 + 釘樁測試 + 開票」而不是 (A) 改架構，理由是：

- **正式路徑踩不到**：生產上 STT 跑在 DO 內的 WS，一次連線＝一個「請求」，緩衝不會被切斷；目前**沒有任何生產呼叫端**。
- **(A) 是 US-104 的形狀**：真正的「會議中即時顯示」需要跨請求的 `pending`，那時緩衝本來就得隨會議狀態持久化
  （同時解掉「換一個 `meetingOffsetMs` 同一句變兩列」），現在硬做會做錯版本。
- **代價我寫清楚了**：設計 §6、交付文 §4、backlog TECH-012 三處都明白寫「對外 API 有靜默漏字的可能」，
  並且用測試把契約釘住（不是只寫在文件裡祈禱）。

### 4. 測試的層次與這一票「最強的一張牌」

三層：單元（4 檔 64 條，含真跡重播）→ 真 workerd 冒煙（`do-smoke.mjs` §8，真的 DO SQLite、真的 HTTP 路由）
→ 既有 35 條 E2E 全綠（本票沒動 UI，所以是回歸）。最強的是**真 workerd** 那一支：
`CREATE TABLE`、UNIQUE 索引、`MAX(seq)+1`、`rowsWritten` 轉接這些都是**平台行為**，
單元測試用的 `node:sqlite` 替身證明不了；第一輪 reviewer 也誠實說「我沒有 shell，不能代替實際綠燈」——
所以母行程自己跑、貼原始輸出。

我也要誠實說兩個**沒有**：真的 WebSocket 連 Deepgram（沒有 Cloudflare 憑證）、以及
`meetingOffsetMs` 的真實延遲值（要連上才量得到）。兩者都只驗「機制正確」與「不得默默當 0」。

### 5. 品質與速度
